# Playwright Core — Shared Rules

> **Scope:** every E2E test under `<e2e-dir>/`. Load alongside `playwright-api` or `playwright-ui` — never alone.
> **Source of truth:** `<e2e-dir>/playwright.config.ts`, `<e2e-dir>/fixtures/`, `<e2e-dir>/services/`, `<e2e-dir>/support/`. If anything below conflicts with the code, the code wins.

## Placeholders

Map these to your own repo before applying the rules:

- `<e2e-dir>` — the root of the Playwright suite (for example `tests/e2e`).
- `<ticket-prefix>` — your issue tracker's project key; ticket IDs look like `<ticket-prefix>-1234`.
- `<fixture-canon-guard>`, `<specs-canon-guard>` — the static checks that enforce the fixtures and specs rules.
- `<local-gate>` — the local script that runs the guard checks in the inner loop and before push.
- `<tag-precommit-hook>` — the pre-commit check that validates test tag IDs.
- `<tag-audit-script>` — the script that reports the next free test ID.
- `<test-state-doc>` — the document that lists expected-failure, skipped and red-by-design tests.
- `<i18n-dir>` — the folder holding the app's translation files, one JSON file per locale.
- `<surface>` — one folder per page or feature area under `specs/ui/`.
- `<backend-helper-dir>` — non-TypeScript snippets that the backend test runner loads.
- `<item-id>` — an item identifier used as seed data.
- `<test-email-domain>` — a domain reserved for test email addresses, for example one you control or a `.test` domain.
- `<resource>` — a domain-specific resource type (for example `document`, `user`, `entry`).
- `<page-name>` — the name of the page or feature area a spec covers.
- `<page-path>` — a relative UI path (for example `/settings`).
- `<api-path>` — a relative API endpoint path (for example `/api/resource`).
- `<area>` — the tag area prefix derived from the spec's folder path; uppercase in practice (for example `AUTH`, `HOME`).

## Directory layout

```
<e2e-dir>/
├── playwright.config.ts          # ALL projects defined here — setup projects + test projects.
│                                 # Read it for the current matrix; don't trust a count in prose.
├── package.json                  # isolated Node project, NOT in root workspace
├── tsconfig.json                 # strict mode
├── .env / .env.example           # SECRETS only
├── test-data/
│   ├── env-config.json           # canonical non-secret config (E2E_BASE_URL, E2E_LOCALE, slugs, …)
│   ├── test-users.ts             # userWithData, guestUser, loggedInUser
│   ├── <resource>-pool.ts, <resource>-variants.ts, …
│   └── test-data.json
├── support/                      # imported helper library — LAYERED BY CONCERN. Canon: support/README.md.
│   │                             # Imports flow DOWN only; a PR-gate guard enforces it.
│   ├── constants/                # cross-cutting static data (locales, timeouts, page-slugs, a11y, …)
│   ├── util/                     # generic page-agnostic helpers (environments, secret-injection, …)
│   ├── mechanism/                # Page/API/lifecycle plumbing (dom-errors, per-test-logger, ci-reporter, …)
│   ├── domain/<area>/            # domain helpers, one folder per area
│   ├── setup/                    # Playwright setup-PROJECT entrypoints + storage-state builders (auth.setup, data.setup, …)
│   ├── <backend-helper-dir>/     # non-TypeScript snippets loaded by the backend test runner (kept as-is)
│   └── analytics-observe/        # analytics observer subtree — LAYERING-EXEMPT (kept as-is, not held to the down-only rule)
├── auth/
│   └── user.json, admin.json     # generated by auth.setup; gitignored
├── services/                     # ApiClient + per-domain Service classes
├── schemas/                      # Zod v4 contract schemas (some re-export from a shared contracts folder)
├── fixtures/                     # Playwright fixtures ONLY. Canon: fixtures/README.md.
│   ├── api-fixtures.ts           # API services, registeredUser, cleanupUser
│   ├── instrumented-page-fixture.ts  # base `page` override (diagnostics/guards) — merged first
│   ├── ui-fixtures.ts            # extends instrumented page + POMs; the UI merge entry
│   └── by-token-fixtures.ts      # guest token-based flows
├── pages/                        # Page Objects (route-scoped). Canon: pages/README.md.
├── components/                   # Component Objects (cross-route widgets)
└── specs/
    ├── api/                      # per-domain folders (auth, health, <resource>, …)
    ├── perf/                     # Lighthouse CWV specs → `perf` project (see playwright-performance)
    ├── analytics-observe/        # assertion-free analytics observation → `analytics-observe` project
    └── ui/                       # one folder per <surface> (e.g. auth, <surface>, navigation),
                                  #   plus the mobile and user-journey folders
```

Auth, resource-manifest, and browser-warmup setup run as Playwright **setup projects** (`auth-setup`, `resource-setup`, `warmup-setup`) that test projects declare via `dependencies`, so each project pays only for the setup it needs.

**Hard rules:**
- Specs only under `specs/`. POMs only under `pages/` or `components/`.
- Spec files must `import { test, expect } from '../../../fixtures/api-fixtures'` (API) or `'../../../fixtures/ui-fixtures'` (UI). Never import from `@playwright/test` directly.
- **Every spec MUST live in a surface subfolder matched by a `playwright.config.ts` project `testMatch`** — `specs/api/<domain>/` or `specs/ui/<surface>/`. A non-`@mobile` spec at `specs/ui/` root is matched by no functional project and **silently never runs** (the `ui-mobile` project's `testMatch` does span `specs/ui/**`, but it only runs `@mobile`-tagged specs — so an untagged root spec still falls through). Full placement rules and the coverage-hole explanation live in `playwright-ui` → "Spec placement".
- **a11y lives in a dedicated per-surface file, inside the surface folder.** Accessibility coverage (keyboard, focus, axe) goes in a `<surface>-a11y.spec.ts` **in the surface's own folder** — `specs/ui/search/search-a11y.spec.ts`, `specs/ui/navigation/nav-a11y.spec.ts` — tagged `@a11y`; functional specs do not carry their own axe runs. What is forbidden is a **cross-surface** a11y grab-bag, or any spec at the `specs/ui/` **root** (matched by no functional project — see above). Full policy: `<e2e-dir>/specs/README.md` §"A11y policy".
- **Confirm the test actually ran.** After adding a spec, verify the intended project executed it (`--list` shows it under a `ui-*`/`api` project, run count > 0). A test no project picks up is as worthless as one that can't fail.

## Fixtures canon (`fixtures/`)

Full rules + checklist: `<e2e-dir>/fixtures/README.md`; enforced by `<fixture-canon-guard>`, wired into the **local** `<local-gate>` (beside the other canon guards), which runs in the inner loop and on the pre-push hook. Note: this is a **local** gate — CI does not run the canon guards today, so the enforcement point when troubleshooting is `<local-gate>`, not a CI job.

**Fixture vs support — the boundary (know this before touching `fixtures/`):**

- A **fixture** is *provisioning with a per-test lifecycle*: it `acquires` a resource (a page, a session, a seeded item/record, a bound service), hands it to the test via `use(value)`, and tears it down afterwards. Its shape is `name: async ({ deps }, use) => { … await use(x); … }`, and a test receives it **by destructuring a named argument** (`async ({ resourcePage, dataSeeder }) => …`). Fixtures live in `fixtures/`.
- **Support** is the *reusable logic a fixture (or spec/POM) calls*: pure helpers (`util/`), Page/APIRequestContext/lifecycle plumbing (`mechanism/`), resource seeding/assertions (`domain/<area>/`), static data (`constants/`), storage-state builders (`setup/`). It has **no `use()` lifecycle** — it's a `function`/`class`/`const` you `import`. Support lives in `support/`.
- **Decision test:** *would the test destructure it as an argument?* → fixture. *Is it a function/class/data that something calls or imports?* → support. If you're writing `export function` / `export const <data>` inside `fixtures/`, it's support in the wrong place — move it to `support/` and import it. A fixture body should **compose** support (call named installers/helpers), not **author** it inline.

The essentials when adding/changing a fixture:

- **A `fixtures/` file exports ONLY fixtures, the composed `test`/`expect`, and fixture-type declarations.** Helpers, data, and Zod schemas live in `support/` (or a POM in `pages/`) and are imported. No `export function` / `export class` / `export default` / bare `export { helper }` — the guard fails the PR. Pass-through `export { x } from "…"` is fine.
- **Fixture bodies are thin wiring.** Acquire → `use()` → teardown is the fixture's whole job — keep that inline. But inline `addInitScript` bodies, route handlers, `page.on(...)` bundles, or any reusable mechanism → extract to a named `support/mechanism/` installer and call it (see `instrumented-page-fixture.ts`, which composes installers).
- **One import surface.** UI specs import `test` from `ui-fixtures`; API specs from `api-fixtures`. The base `page` instrumentation is `instrumented-page-fixture.ts` (merged first), never re-inlined.
- **Config knobs:** run/CI-wide → env var (`E2E_LOCALE`, `E2E_TARGET`); per-describe override → `[default, { option: true }]` + `test.use()`.
- **Naming:** `*-fixtures.ts` or `instrumented-page-fixture.ts`; kebab-case; never `utils`/`helpers`/`misc`.

## Specs canon (`specs/`)

Full rules + checklist: `<e2e-dir>/specs/README.md`; enforced by `<specs-canon-guard>`, wired into the **local** `<local-gate>` (the E2E lane, beside the pom/fixture/support guards). Report-only until the existing tree is green, then switch the guard to blocking mode (`<specs-canon-guard>` documents how). Local gate only — CI does not run the canon guards.

**A spec is ORCHESTRATION + ASSERTIONS. Nothing else.** It composes fixtures + POMs + support + test-data into a scenario and asserts the outcome. Locators, data, mocks, API plumbing, and UI strings each have a home that is NOT the spec.

**The #1 rule — reuse first, never build in isolation:** before you author *anything* in a spec — a locator, a data factory, a route mock, an API call, an expected string — **search `pages/`/`fixtures/`/`support/`/`test-data/`/`<i18n-dir>` for an existing one and reuse or extend it.** Create new only when nothing exists, and put the new thing in its proper home, not the spec. (This mirrors the repo-wide "reuse existing components" rule.) A spec that re-implements what the framework already owns is a regression even when green — it's why the suite drifted into isolated islands.

Extraction destinations (what moves *out* of a spec):

| Smell in a spec | Home |
|---|---|
| `page.route(...)` mock builder | `support/mocks/<area>/*-mocks.ts` |
| `buildRecord`/`buildItem`/seed IDs | `test-data/<area>.ts` or `support/domain/<area>/` seeder |
| Hand-typed UI string (`'<action> succeeded'`) | app i18n via reader (`<i18n-dir>`); gap literals → `support/`/`test-data/` |
| `page.request.get('/api/…')` + `Bearer` | the api fixture / `support/domain/<area>/` |
| `.locator('[data-testid=…]')` | a POM getter under `pages/` |
| `const TEST_LOCALE = 'en-gb'` | delete — use the `locale` fixture |

**Assertion oracles (three tiers) — the expected value must be independent of the code under test:**
1. **Computed (computed values/totals/dates/counts):** the test derives the expected value itself (pinned constant or in-test re-computation). NEVER read a computed total from the app or a service and assert the app shows it. A service value may be used only as *seed input*, never as the expected output. No "ask the app the total" helper exists or may be added.
2. **UI text:** prefer semantic state (`data-state="approved"` via a POM getter) — locale-proof. When wording *is* the behaviour, oracle = the app's own translation read from `<i18n-dir>/<locale>.json` by key (tests wiring, not linguistics). Never a hand-typed English literal in a spec.
3. **Existence/structure:** POM `data-testid` presence — weakest, pair with tier 1/2.

**What `<specs-canon-guard>` enforces (hard):** import the composed `test`/`expect` from `fixtures/` (never raw `@playwright/test`); no inline `[data-testid]`/`[data-action]` locators; no hardcoded locale; no spec-level `try/finally` teardown; no cross-test mutable module state; kebab-case `*.spec.ts` filename with no banned context-free leaf name; only `*.spec.ts` files under `specs/`. Plus report-only smells (oversized file, inline data/mock factory, multiple `page.route`).

**Canon-required but NOT checked by this guard** (documented in `<e2e-dir>/specs/README.md`; enforced by review or other gates): one-level tab foldering (~≥6-file clusters), a11y consolidation (dedicated `*-a11y.spec.ts` + single `@a11y` tag + shared runner), and the tag/`test.step` discipline (owned by `<tag-precommit-hook>` + the `test.step` section below). Do not describe these as guard-enforced.

## Configuration

### Two-tier config — `env-config.json` for non-secrets, `.env` for secrets only

`<e2e-dir>/playwright.config.ts` reads `test-data/env-config.json` first, then layers `.env` on top via `dotenv`. The JSON file is the canonical source for `E2E_BASE_URL`, `E2E_LOCALE`, slugs, and seed fixtures. The `.env` file holds only secrets.

`E2E_BASE_URL` is read from `env-config.json` and **ignores shell env**, so a stale exported variable cannot point the suite at the wrong origin.

### `baseURL` is origin-only

`baseURL` = `scheme://host[:port]`. The locale lives in the test path, not the config. Use `uiPath(locale, '/<page-path>')` and `apiPath(locale, '/<api-path>')` from `support/constants/locales.ts` — never inline `/en-gb/...` strings.

```ts
// ✅
await page.goto(uiPath(locale, '/<page-path>'));
await request.get(apiPath(locale, '/<api-path>'));

// ❌ baking locale into baseURL — breaks every other locale and the /api/* prefix
E2E_BASE_URL=http://localhost/en-gb
```

Production routes `/api/*` and `/<locale>/*` from the **same origin**. One origin-only `baseURL` is shared by both `page.*` and `request.*`.

### Locales — `LOCALES` vs `RELEASED_LOCALES`

`<e2e-dir>/support/constants/locales.ts` is the source of truth (don't hardcode a locale list from prose):

- **`LOCALES`** — the canonical universe. Used for the `Locale` type, `E2E_LOCALE` validation, and coverage data.
- **`RELEASED_LOCALES`** — the subset actually live (the default is the currently live subset, overridable with a comma-separated `E2E_RELEASED_LOCALES` env var, validated against `LOCALES`). **Specs that loop over locales to *run* them must iterate `RELEASED_LOCALES`, not `LOCALES`** — otherwise unreleased locales fail the suite. `isReleasedLocale(locale)` guards single-locale checks.

The default locale per run comes from `env-config.json` and is exposed as the `locale` fixture in both `api-fixtures.ts` and `ui-fixtures.ts`. Override per run with `E2E_LOCALE=en-gb make test-e2e`. Full locale rules: `playwright-locale-validation`.

## Test titles — plain-language behaviour first

A test title is the first thing a human (engineer, PM, or new joiner) reads in CI. It must
say **what behaviour is guaranteed and why it matters**, in words a non-engineer understands —
not just the HTTP verb, path, schema class, and status code.

**Title template:**

> `<plain-language subject + action + expected outcome> (<technical scope: METHOD path → status / contract>)`

**Rules:**

1. **Lead with behaviour a non-engineer understands** — what the system/user does and what
   *should* happen. Domain words (the resource loads, the action succeeds, the request fails), not
   implementation (`ResourceSchema`, `contract validation`).
2. **Always name the subject.** Never `returns 200 + FooSchema` — say *what* returns it.
3. **Jargon goes in the trailing parentheses.** Schema names, status codes, field names, and
   paths are useful to engineers — keep them, but as the technical scope in `( … )`, never as
   the whole title.
4. **Describe intent, not mechanism.** "loads with a complete, valid structure", not "parses
   strictly against the schema".
5. **No ticket IDs and no bare `Step N` in the title.** Tickets live in tags/comments; if it's
   a step in a journey, name the step's *purpose* (e.g. `${item}: options load…`),
   not `Step 1`.
6. **Clarity beats brevity.** A longer, unambiguous title wins over a short cryptic one.

```ts
// ❌ implementation-only, no subject / outcome / point
test('returns 200 + ResourceSchema', …)
test('<ticket-prefix>-1234 — response parses against the contract (available + key)', …)
test('Step 1 — resource data is structurally valid and matches expectations', …)
test('responds within 2000 ms', …)

// ✅ behaviour first, technical scope in parens, no ticket/step in the title
test('Resource list loads and is well-formed (GET /<api-path> → 200; nested id/name/slug tree)', …)
test('Add-on options each load with a valid code (GET /<api-path> → 200; available + key)', …)
test(`${item}: options load with a valid structure (GET /<api-path>/${key}; variants)`, …)
test('The homepage content loads within 2 seconds (GET /cms/homepage)', …)
```

### The scenario lives in the title, not a comment

The `test(...)` title **is** the scenario — a full behaviour-first sentence a non-engineer
reads and understands. Do **not** add a `/** … */` doc block above a test that merely restates
the title; that is two things to keep in sync and it rots.

A block comment above a test is earned **only** by context the title can't hold: a data
precondition, a "red-by-design / feature unbuilt" note, or *why* this scenario matters. If the
comment would just paraphrase the title, delete it.

```ts
// ❌ doc block restates the title — delete it
/** Verifies the record summary is correct. */
test('Record summary shows correct subtotal, tax, and total for a configured item', …)

// ✅ title carries the scenario; no redundant comment
test('Record summary shows correct subtotal, tax, and total for a configured item', …)

// ✅ comment earns its place — it explains a non-obvious precondition the title can't
// This fixture is the only one with a tiered add-on, so the totals include it.
test('Record summary includes the add-on line for a tiered item', …)
```

## `test.step()` is mandatory

Every logical block goes inside `await test.step()`. Bare `expect()` in a test body is forbidden.

### Two step kinds — action steps and verify steps

A step either *does* something or *checks* something. Name it for what it is:

- **Action / setup steps** (navigate, click, fill, select, seed, intercept, capture) use an
  **imperative verb** describing the action: `Navigate to the page`, `Select an inactive option`,
  `Intercept a third-party request and abort it`. They contain no `expect()` (beyond an
  action-macro pre-gate inside a POM). Do **not** force these into the `Verify …` mould.
- **Assertion steps** (any step containing an `expect()`) use the `Verify …` model below.

There is no third form. The legacy `Assert:` / `Assert` prefix is retired — an assertion step
starts with `Verify`.

```ts
// ✅ action step — imperative, no expect()
await test.step('Navigate to the page', async () => { await resourcePage.goto(locale); });
await test.step('Select an inactive option to trigger the update', async () => { … });

// ❌ action step forced into Verify — awkward and wrong
await test.step('Verify the page is navigated to', async () => { … });
// ❌ retired Assert prefix
await test.step('Assert: value is visible', async () => { … });
```

### Assertion-step title format — `Verify <plain meaning>` + Expected/Actual

Assertion-step titles use the **`Verify …` model**: start with `Verify`, then say
**in plain language what is being checked** (the meaning, not the mechanism), then the
`Expected: X, Actual: ${y}` value/state form. Lead with what a non-engineer would
understand; put the raw field/schema/status detail after it.

```ts
// ✅ Verify + plain meaning + interpolated Actual
await test.step(`Verify the request succeeds (Expected: 200, Actual: ${response.status()})`, async () => {
  expect(response.status()).toBe(200);
});

await test.step(`Verify the user lands on the expected page (Expected: /${locale}/<page-path>, Actual: ${page.url()})`, async () => {
  await expect(page).toHaveURL(new RegExp(`/${locale}/<page-path>`));
});

await test.step(`Verify at least one record is returned (Actual: ${body!.data.length})`, async () => {
  expect(body!.data.length).toBeGreaterThan(0);
});

// ❌ no step
expect(response.status()).toBe(200);

// ❌ mechanism, no plain meaning
await test.step('Verify body parses against ResourceResponseSchema', async () => { … });
// ✅ say what it means
await test.step('Verify the response data comes back in the expected shape', async () => { … });

// ❌ step exists but actual value not interpolated
await test.step('Verify status code is 200', async () => {
  expect(response.status()).toBe(200);
});
```

### Grouping

- One step per HTTP call (`ApiClient` does this automatically).
- One step per logical assertion group. Use `expect.soft()` inside the step for multiple independent fields.

### Null-guard before `body!.field`

`parseResponse` returns `body: T | null`. Always assert non-null before dereferencing or a degraded 5xx response surfaces as `Cannot read properties of null` instead of the real assertion failure.

```ts
expect(body, 'Health body should parse against schema on 200').not.toBeNull();
expect(body!.status).toBe('healthy');
```

### Latency tests need a warmup

The first request in a worker pays connection + DNS + reverse-proxy upstream-pool warmup. Throwaway warmup, then measure:

```ts
await healthService.getHealth();      // warmup
const start = Date.now();
const { response } = await healthService.getHealth();
const duration = Date.now() - start;
expect(duration).toBeLessThan(2000);
```

### Fixture traceability

Fixtures that perform I/O (HTTP calls, DB writes, file writes) wrap setup and teardown in `await test.step('Fixture Setup: …')` / `await test.step('Fixture Teardown: …')`. Without this, fixture failures show as opaque Playwright internals like `Fixture "request"` and you can't tell what broke.

```ts
recordWithItem: async ({ resourceService }, use) => {
  let recordId: string | undefined;
  await test.step('Fixture Setup: create record with item', async () => {
    const { body } = await resourceService.createWithItem({ id: '<item-id>', quantity: 1 });
    recordId = body.id;
  });
  try {
    await use(recordId);
  } finally {
    await test.step('Fixture Teardown: delete record', async () => {
      if (recordId) await resourceService.delete(recordId);
    });
  }
}
```

Trivial fixtures that only `new` a service class don't need step wrapping.

## File header comment — purpose, not traceability codes

Every spec opens with a `/** … */` header that says, in plain language: **what surface** the
file covers, **what it guarantees**, and any **runtime prerequisites** (env vars, stack). That's
it.

Do **not** carry:

- **Traceability code lists** (`F-09, C-32, S-14, Z-04`) — no gate reads them; they rot.
- **Test-ID enumerations** (`Tests: U-PDP1–U-PDP7`) — the canonical `@AREA-TYPE-NNN` tag on each
  test is the trace handle (see §Tagging). Duplicating IDs in the header just drifts.

One optional `Epic: <ticket-prefix>-1234` line (with its tracker URL) is fine when the file exists to satisfy
a single ticket/epic — it's the one durable external reference.

```ts
// ✅
/**
 * <page-name> — UI spec.
 *
 * Guarantees the page renders its core surface: title, main content,
 * interactive controls, graceful degradation when a dependency is
 * unreachable — plus an axe-core a11y pass.
 *
 * Prerequisites:
 *   - E2E_RESOURCE_SLUG (the resource this spec uses) in `<e2e-dir>/.env`
 *   - Local stack up: make docker-up
 */

// ❌ rotting metadata no gate enforces
/**
 * UI spec: <page-name>
 * Traceability: F-09, C-32, C-33, C-34, S-14, Z-04, B-04, B-05, …
 * Tests: U-001–U-007, U-008-R
 */
```

## Known-issue guards: `test.fail()` is the default — not `test.fixme()`

**A confirmed, ticketed defect on a single-assertion guard is marked `test.fail(true, '<ticket-prefix>-#### — …')`, NOT skipped or fixme'd.** This is the mechanism that lets a CI leg full of known-issues still serve as a promote **gate**:

- The test **RUNS every time** and confirms the defect still reproduces (a skip verifies nothing and silently rots when its ticket resolves).
- A **known** (expected) failure does **not** fail the leg → the leg stays green and can gate.
- The leg turns **RED** only when it should: the guard starts **passing** (defect fixed → delete the marker, let it guard green) or a *different* un-annotated test fails (a real regression).

```ts
// ✅ known ticketed defect — runs, confirms, does not fail the gate, flips red when fixed
test('A tampered value is rejected before save (POST /<api-path> → 4xx)', { tag: ['@<area>-API-004'] }, async ({ resourceService }) => {
  test.fail(true, '<ticket-prefix>-1234 — tampered value accepted (known defect)');
  …
});
```

**Reason format (mandatory — the ticket is machine-parsed).** The `test.fail()` reason MUST lead with the ticket ID, then ` — `, then the defect in plain words:

```ts
test.fail(true, '<ticket-prefix>-#### — <what is broken> (known); expected-fail keeps the gate green until fixed');
```

The ticket is not optional and not a trailing aside. The CI reporter (`<e2e-dir>/support/mechanism/ci-reporter.ts`) reads it out of the `fail` annotation and prints it on the expected-fail summary line — `<area>-UI-021 — <ticket-prefix>-2364 listing page "…" passes an axe-core scan` — so a promote reviewer can see WHICH ticket each tolerated red belongs to without opening the spec. A reason with no parseable ticket (`[A-Z]{2,}-\d+`) renders as `NO-TICKET` in that summary: a loud canon violation, not a silent one. (Exempt: a genuine data/env-precondition `test.fail(<condition>, …)` — e.g. `isProdTarget()` when the production target has no historical record yet — which is not a bug and carries no ticket.)

**`test.fail()` caveats — do NOT use it when:**
- The test is a **multi-step journey.** `test.fail` marks the WHOLE test, so it suspends all downstream coverage and silences a smoke light. Use `expect.soft` (leg stays red) or leave red-by-design instead.
- The guard is **flaky** — intermittent passes will red the leg with "expected to fail but passed".
- Remember it checks only *that the test failed*, not *why* — a guard breaking for a NEW reason stays green. Acceptable for single-purpose guards; the ticket documents intent.

### A hard red still carries its ticket: the `known-issue` annotation

A test left **red-by-design** (the case above — a journey, where `test.fail` is forbidden) has no `fail` annotation to carry its ticket, so it used to print as a bare title and a reviewer could not tell a tracked defect from a fresh regression. Declare the ticket in the `test()` options instead:

```ts
test(
  'logged-in user completes the core path: …',
  {
    tag: ['@smoke', '@core-journey'],
    annotation: { type: 'known-issue', description: '<ticket-prefix>-#### — <what is broken> (red-by-design)' },
  },
  async ({ page }) => { … },
);
```

Same `<ticket-prefix>-#### — …` format as a `test.fail` reason, and the reporter machine-parses it the same way. Two rules:

- **Declare it in the `test()` signature — never `test.info().annotations.push()` at runtime.** The point is to survive a test that dies before reaching any of its own statements.
- **It reads "on file", not "this red is that ticket".** A test-level annotation cannot distinguish the tracked defect from a NEW break in the same test, so the reporter prints `[<ticket-prefix>-1234 on file]` plus "confirm the error matches" rather than presenting the red as explained. Do not reword it into a claim.

Full state taxonomy (expected-failure / red-by-design / soft-asserted / skipped / masked) lives in `<test-state-doc>`.

## `test.skip()` vs `test.fixme()` — guard vs parked

Two different intents; the message rule differs:

- **Guard-skip** — *conditional, runtime*: this run's env/data can't exercise the path
  (`test.skip(optionCount < 2, …)`). The message must state **why this run can't cover it** —
  name the missing var / data / env. **No ticket needed**; there's no bug to track.
- **Parked-skip / fixme** — *unconditional*: use ONLY when the subject genuinely cannot be
  exercised (feature unbuilt, endpoint absent) — and even then prefer **deleting** the test until
  the feature ships (a skipped stub rots). A defect that *does* reproduce is a `test.fail()`
  guard (above), never a fixme. Any parked test **must carry a ticket** (`<ticket-prefix>-####`)
  in the message or an adjacent comment.

`test.step.skip(...)` follows the same split, and the reason goes **in the step title**.

The mechanical test: `.skip(true` / `.fixme(true` / `.fixme(<title>` / `describe.fixme` ⇒ parked
⇒ ticket required. `.skip(<condition>, …)` ⇒ guard ⇒ why required, ticket optional.

```ts
// ✅ guard — why, no ticket
test.skip(count === 0, 'Option rows are not rendered in this flow');
test.skip(locale !== 'en-gb', 'This behaviour applies only to the en-gb locale');

// ✅ parked — ticket required
test.skip(true, 'A third-party API returns {"success":false} for this item; the dependent block never renders — <ticket-prefix>-1234');
test.fixme('A tampered value is rejected before save (POST /<api-path> → 4xx)', { tag: ['@<area>-API-031'] }, …);

// ✅ step-level skip — reason in the title
await test.step.skip('Verify accessibility (parked: two known app-side axe violations — <ticket-prefix>-1234)', …);

// ❌ parked with no ticket
test.skip(true, 'flaky, will fix later');
```

## Inline comments — explain WHY, never WHAT

An inline `//` comment is justified only when it explains something the code **cannot** say: a
non-obvious rationale, a workaround for an app/data quirk, a deliberate omission, or a
"red-by-design" note. Cite tickets as bare `<ticket-prefix>-####`.

If the comment restates what the next line does, delete it — the code and the step title already
say it.

```ts
// ✅ WHY — a non-obvious app behaviour the reader would otherwise trip on
// <ticket-prefix>-1234 renders all options open — there is no "expand" step. Pick the first
// selectable option that isn't already active and isn't the "+N more" overflow.
const selectableOption = resourcePage.optionItems.and(…).first();

// ✅ deliberate omission
// Not every option changes the displayed value (same-tier selection), so we assert the value
// stays visible and valid — not that it changed.
await expect(resourcePage.displayedValue).toHaveText(/\d/);

// ❌ narrates the next line — delete
// Click the first facet option
await facet.first().click();
```

## Tagging

### Three mandatory tier tags + supplemental metadata

| Tier tag | Meaning | Runs in |
|---|---|---|
| `@smoke` | Minimal liveness — system is up and the critical-path responds | PR open (`CI_STAGE=smoke`) |
| `@happy-path` | Standard positive flows — contract verified | PR merge gate (`CI_STAGE=pr`) |
| `@regression` | Negative paths, validation failures, auth failures, edge cases, rate limits, boundaries | Nightly on master (`CI_STAGE=nightly`) |

Every test carries **at least one** tier tag. `@smoke + @regression` is allowed for critical-path negatives (e.g. login 401). `@smoke + @happy-path` is forbidden — pick one tier.

### Supplemental metadata tags (additive, not a replacement for a tier)

| Tag | When | Where it shows up |
|---|---|---|
| `@api` | API specs — applied at `describe()` for the whole file | `specs/api/**/*.spec.ts` |
| `@ui` | UI specs — applied at `describe()` for the whole file | `specs/ui/**/*.spec.ts` |
| `@mobile` | Test exercises a genuinely mobile-specific flow or layout | `ui-mobile` project |
| `@external` | Test depends on a live third-party service — CI may filter on flaky external dependencies | `specs/api/<third-party-domain>` |
| `@userjourney` | Full end-to-end user journey flows — runs in the dedicated `ui-userjourney` project post-staging | `specs/ui/user-journey/**` |

A test always has at least one tier tag. Metadata tags are added on top.

> If the project uses third-party tools of this kind, update this skill to handle them. If it does not, skip this instruction.

### Canonical test ID — exactly one `@AREA-TYPE-NNN` per test

Each test carries **one** stable ID tag — `@<area>-UI-013`, `@<area>-API-031`, `@<area>-PERF-002` —
plus **one** `@AREA-AXE-NNN` if (and only if) its body runs axe-core. The ID is the
rename-stable trace handle: the title is behaviour-first plain language and *will* change, but
the ID follows the test through history, the QA roadmap, and CI. This is enforced by the
pre-commit tag gate (`<tag-precommit-hook>`): a classified test with no
ID, a wrong `AREA`/`TYPE` for its path, or a **duplicate** ID blocks the commit.

Rules:

- **Exactly one** primary ID per test. Two primary IDs on one test (`… '@<area>-UI-002',
  '@<area>-UI-008' …`) is the duplicate-ID error waiting to happen — the second is dead weight and
  will collide with whatever test legitimately owns it. Same for AXE IDs.
- `AREA` and `TYPE` are derived from the file path (the path-to-area map inside the tag gate); don't
  hand-pick them.
- Get the next free counter from the tag audit (`node <tag-audit-script>`) — never guess a number.
- The ID belongs in the **tag array**, never as a title prefix.

```ts
// ✅ one primary ID (+ one AXE ID because the body runs axe)
test('<page-name> passes an axe-core accessibility scan', { tag: ['@ui', '@smoke', '@<area>-UI-013', '@<area>-AXE-003'] }, …)

// ❌ two primary IDs on one test — duplicate-ID error, second is noise
test('<page-name> loads with title, image, and content', { tag: ['@smoke', '@<area>-UI-002', '@<area>-UI-008'] }, …)
```

### Multi-tagging — array syntax only, never a comma-string

```ts
// ✅
test('A-H1', { tag: ['@api', '@smoke'] }, async ({ healthService }) => {});
test('login wrong password', { tag: ['@smoke', '@regression'] }, async () => {});

// ❌ comma in a single string
test('login', { tag: '@smoke, @regression' }, async () => {});
```

Tag at `describe()` level when the whole block shares one behaviour; per-test when behaviours are mixed.


## Soft assertions

When validating multiple **independent** properties of a single response or component, `expect.soft()` is mandatory. Hard `expect()` halts at the first mismatch and forces N re-runs to surface every contract gap.

```ts
expect(response.ok()).toBeTruthy();   // hard — gate

await expect.soft(body!.services.redis.status, 'redis status').toBe('ok');
await expect.soft(body!.services.database.status, 'database status').toBe('ok');
await expect.soft(body!.services.database.driver, 'database driver').toBe('pgsql');
```

**Critical:** never soft-assert a step that subsequent code depends on. Soft-asserting `response.ok()` and then calling `response.json()` on a 500 produces a misleading parse error instead of a clear contract failure.

| Use hard `expect()` for | Use `expect.soft()` for |
|---|---|
| `response.ok()` / status code gate | Multiple independent fields of a parsed response |
| Page navigation completing before next action | All properties of a fully-received UI component |
| Fixture assertion that gates the test body | Multi-field form / record-summary checks |

Pass a descriptive string as the second arg — it appears verbatim in the failure report.
